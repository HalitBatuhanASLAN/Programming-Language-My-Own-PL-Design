1e-9 lexes as: INT_LITERAL(1) IDENTIFIER(e) OP_MINUS(-) INT_LITERAL(9) → ParseError at IDENTIFIER 'e' (expected , or }). Root cause: float_literal grammar has no exponent rule.

Maximal munch: == never tokenizes as two separate =. 2-char ops ordered before 1-char in TOKEN_SPEC regex.

Architecture: single compiled master regex (TOKEN_SPEC). WORD matches all identifier-shaped strings first → post-classification step assigns KEYWORD / METRIC_LIT / BOOL_LIT / IDENTIFIER via frozenset lookup. Token dataclass: type, value, line, column. Custom LexicalError with exact location.

Operator Precedence (§7.3 — stratified nonterminals)
LevelOpAssocNonterminal
1 lowestorleft<expr>

3notright-recursive<not_expr>
4== != < <= > >=left, non-chain<rel_expr>
5+ −left<add_expr>
6* /left<mul_expr>
7 highestunary −right-recursive<unary_expr>

not and unary− are RIGHT-RECURSIVE, NOT right-associative. Associativity is a binary operator concept (§7.3). not not x parses as not(not x) via recursion, not associativity. AI generated "right-associative" — you corrected to "right-recursive".

Relational ops are NON-CHAINING: a < b < c is a ParseError, not double comparison — prevents Python-style silent logical errors.

Left-assoc via while-loop: left = BinOp(op, left, right) in loop. Recursion → right-assoc + infinite loop risk for top-down parser.

Revision Defense — analyze block semicolons vs commas (§1.3.1 vs §1.3.2)

CHANGE: Part 1 used comma-separated fields → Part 2: semicolon-terminated, no inter-field separator.

FINAL GRAMMAR: <analyze_field_list> ::= <analyze_field> { <analyze_field> } <analyze_field> ::= "threshold" "=" <float_lit> ";" | "underfit_max_acc" "=" <float_lit> ";" PARSER LOOP: while current.type=='KEYWORD' and current.value in ('threshold','underfit_max_acc'): parse_field() # consumes field keyword, =, float_lit, ;

Why NOT {field ','}? Comma doesn't exist between fields — loop consuming it raises ParseError. Lookahead on field keyword is the only reliable termination condition.

DEFENSE (§1.3.1 readability): Self-delimiting — reader scanning block sees complete terminated unit on each line without tracking whether comma follows. Consistent with verbose keyword style (higher_is_better, overfitting_analysis, etc.).

COUNTER (§1.3.2 writability / D5 retrospective): analyze block is the ONLY construct in Ayar using semicolon terminators. Model blocks, report blocks, metric lists all use commas. Inconsistency imposes writability cost — programmer must remember different convention for ONE block type. Multiple correction rounds during development materialized this cost.

VERDICT (D5): Retrospective wins. Marginal readability gain from semicolons, concrete recurring writability cost. Would use uniform commas if starting over.

Heap-dynamic—NOT IN AYAR—

Lookup: Experiment scope first → not found → Global scope. Model declared at top-level visible to every experiment block.

Why not dynamic? Dynamic: train m inside experiment B could accidentally resolve to experiment A's m if scopes not isolated → nondeterministic training results → ML reproducibility destroyed. Static: reading source code tells you exactly which model is used — no runtime call history needed.

What breaks if switched? Two experiment blocks both declaring local model m → second experiment's train m picks up first experiment's m → silently different hyperparameters used → unreproducible results, catastrophic in ML.

Parser Architecture (Sebesta §4.4)
  • Recursive-descent, LL(1): one _parse_* method per EBNF non-terminal
  • _consume(expected_type): gate method → ParseError with expected/actual/line/col
  • Left-assoc via while-loop (NOT recursion)
  • validate_layout() pre-parse pass: { and } on own lines → LayoutError (NOT ParseError — EBNF cannot express line-position constraints)
  • AI parser bugs: 8 token name mismatches (ASSIGN→OP_ASSIGN, INT_LIT→INT_LITERAL), split ratio INT→FLOAT, analyze comma→none, missing dotted eval_target third alternative
    • Design Decisions Q&A (Sebesta-rooted)
    Q: Why does Ayar use closed keyword set for model types instead of open identifiers?
    A: Deliberate DSL design decision — validates model types at SYNTAX level, not semantic level. Parser immediately rejects "RandomForest" with a helpful message listing valid types. AI recommended D1 to make them open identifiers (E1 experiment) — rejected because DSL's identity relies on constraining the type space. Trade-off: user cannot add new model types without grammar change. Intentional — language defines the support set.
    Q: Why is layout rule (brace on own line) a pre-parse pass, not EBNF?
    A: EBNF describes token sequences — it cannot express constraints about line positions. { is a valid SEPARATOR token regardless of which line it's on. The layout validation pass (validate_layout) inspects line number attributes of tokens — information only available post-tokenization. Raises LayoutError, not ParseError, to distinguish the two error sources.
    Q: Ayar prioritizes readability (§1.3.1) — give 3 concrete grammar choices that reflect this.
    A: (1) { must be on its own line — forces visual block structure. (2) Verbose keywords: higher_is_better, lower_is_better, overfitting_analysis — ML researcher reads intent immediately. (3) Separate keywords for each pipeline step: train, evaluate, collect, analyze, compare, exclude, select — each statement type named explicitly, no abbreviations. Trade-off: all three increase writability cost (§1.3.2).
    Q: Why is the expression sub-language (add_expr, mul_expr etc.) defined but never semantically grounded in §4.4?
    A: Scope decision consistent with handout (only 2 constructs formalized). Expression sub-language has no evaluation rules. This left R3 as dead code — grammar prevents metric literals in arithmetic positions, so R3 can only be triggered via synthetic AST. D5 retrospective identifies this as a visible gap: expression sub-language would need its own evaluation semantics and proper type judgement system in a real implementation.
    Q: Why not short-circuit evaluation for or/and? (§7.6)
    A: Ayar expressions have NO side effects — short-circuit only helps when evaluating second operand has a side effect to skip. In exclude if overfit or underfit, both tags are pre-computed Booleans already available before the exclude statement runs. Full evaluation: behavior completely predictable regardless of operand order → supports reliability (§1.3.3). Future extension trade-off: if conditions become computationally expensive, full eval wastes work.
    Q: Relational operators are non-chaining — why? (§7.3)
    A: a < b < c looks like a double comparison in math but Python evaluates it as (a < b) and (b < c) — a semantic that surprises C/Java programmers. Ayar makes a < b < c a ParseError at the second relational operator in <rel_expr> — no silent misinterpretation possible. Reliability (§1.3.3) over writability.
    Q: Model types as closed keyword set — what would happen if user wrote model XGBoost m?
    A: Lexer tokenizes XGBoost as IDENTIFIER. Parser expects <model_type> (one of the 5 keywords) after "model" keyword — sees IDENTIFIER instead → ParseError: "Expected model type (KNN, DecisionTree, SVM, NaiveBayes, LogisticRegression), received IDENTIFIER 'XGBoost'". Language design time binding: model type set is fixed in grammar, not user-extensible.
    Q: Why does eval_target have 3 forms (plain, dotted, bracket)?
    A: Plain: evaluate some_model on d.test (pre-selected model). Dotted (iris_exp.best): preferred form, reads naturally as "the best from iris_exp". Bracket ([iris_exp.best]): alternative syntactic sugar. AI's initial parser only had plain and bracket — dotted form was missing. Caught by tracing D1 sample program through grammar by hand. Parser must try dotted form FIRST — otherwise iris_exp matches plain id and .best becomes stray token → ParseError.
    Q: Why does Ayar have no heap-dynamic variables?
    A: Ayar is a high-level DSL for ML configuration — abstracts away low-level memory concerns. No manual allocation/deallocation needed. This is consistent with reliability priority (§1.3.3) — heap management introduces entire classes of bugs (leaks, dangling pointers) irrelevant to the domain. Stack-dynamic (experiment scope) and static (global) cover all needed lifetimes.
    Q: From Part 1 — Why did you keep model types as closed keywords instead of open identifiers (AI recommendation D1)?
    A: AI's E1 experiment recommended making model types open identifiers — rejected because parser validates model types at syntax level, which is the DSL's identity argument. A language where model KNN and model MyCustomNet are syntactically equivalent is not a DSL but a generic scripting language. Closing the set to 5 types is a deliberate constraint that can be defended at the exam: Sebesta §3.3 — closed keyword sets make grammars unambiguous and error messages more helpful.
