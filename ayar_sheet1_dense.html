metric and float: IDENTICAL underlying rep (ℝ) but DIFFERENT TYPE NAMES → name equivalence forces them apart. This is the single most important design decision in Ayar.

Strong Typing (§6.12) — 3 enforcement points
  • ① metric ≠ float → TYPE CHECKER, Rule R3 — BinOpNode with MetricLiteralNode rejected
  • ② Model field type → PARSER — <field_value> only int|float|str|bool — metric forbidden here syntactically
  • ③ Dataset ref type → PARSER — <dataset_ref> ::= id '.' split_role — bare model name cannot match

    • Detecting accuracy+0.5 at PARSE time (not type-check time) STRENGTHENS §6.12 — strong typing only requires detection, not specification of when.

    Coercion (§7.4) — ONE implicit rule
  • ALLOWED: int → float (widening) only — Python numeric promotion at BinOpNode eval in interpreter
  • FORBIDDEN: float→int (no narrowing) / metric→float (name eq blocks) / bool→int

    • WHERE implemented: NOT in TypeChecker (no T⊢e:τ judgement rules). Grounded in INTERPRETER via Python widening. D1 §4.5 = design intent; §4.7 = formal grounding.

    Follows Java / §7.4: widen freely, never narrow silently.

    State Triple σ = (Γ, M, R) — Sebesta §3.5
  • Γ = Name → Value — global env: datasets & models
  • M = ModelName → MetricMap — training results (stack-dynamic, DISCARDED at block exit)
  • R = ModelName | ⊥ — best selection; ⊥ until select best fires

    • MetricMap = MetricName → ℝ where MetricName ∈ {accuracy, precision, recall, f1}

    E-ExperimentBlock — THE BUG + FIX (Part 1→Part 2)
    BUGGY (Part 1): ⟨exp name {s₁…sₙ}, (Γ,M,R)⟩ → (Γ[name.best↦R'], M', ⊥) ← M' LEAKED! FIXED (Part 2): ⟨exp name {s₁…sₙ}, (Γ,M,R)⟩ → (Γ[name.best↦R'], M, ⊥)

    WHY: M is stack-dynamic (§5.8.2) — internal metric data must be DISCARDED when block closes. Only exp_name.best survives via export to Γ. Outer M restored unchanged.

    IMPL: block entry → self._M = {} | exit → self._gamma['e.best'] = self._R (M never written back)

    Found via AI consistency audit (D4 Entry #1) — formal rule directly contradicted its own prose explanation. Caught by cross-referencing §4.4 rule against §4.6 stack-dynamic lifetime declaration.

    WHY: E-Train precondition dataset_ref ∈ dom(Γ) was formally ungrounded without E-DatasetDecl. No rule established how dataset name enters Γ — precondition formally unprovable.

    WHY NOT add report_stmt/top-level eval_stmt rules? Handout allows only 2 constructs. Those have no unfulfilled preconditions in existing rules → adding them over-specifies and creates unnecessary obligations.

    Compare–Exclude–Select Pipeline
  • P-AnalyzeOverfitting: TAGS models {overfit, underfit}. NO removal. overfit(n) ⟺ M(n)(train_acc) − M(n)(val_acc) > threshold | underfit(n) ⟺ M(n)(val_acc) < underfit_max_acc
  • P-Compare: ranked = sort(dom(M), by metric, order direction)
  • P-Exclude: M' = {n | ¬overfit(n) ∧ ¬underfit(n)}
  • P-SelectBest SUCCESS: dom(M')≠∅ → best_name = first(ranked(M')) → R = best_name
  • P-SelectBest FAILURE: dom(M')=∅ → NoEligibleModelError (loud failure §1.3.3 reliability)

    • TWO-STEP design (tag then filter): P-AnalyzeOverfitting tags but does not remove. P-Exclude filters using those tags. Reason: separates concern of analysis (what is the model's fitness status?) from concern of policy (which models eliminate?). Readable independently. Consistent with E-Sequence sequential structure — tagging must precede filtering in state; combined rule would hide this requirement.

    eval_accuracy field: separate field in ModelResult, NEVER touched by E-Collect. Without it: after collect metrics [f1,precision], analyze reads metrics.get('accuracy',0.0)=0.0 → tags ALL as underfit. Real bug found during stress testing with sample_2.ayar.

    Design Decisions Q&A (Part 2 focus)
    Q: Why choose name equivalence for metric over structural?
    A: Structural eq would treat metric and float as same (both ℝ) → accuracy+0.5 silently compiles → wrong model selected without any error. Name eq draws a hard line by type name alone regardless of representation. Trade-off: user cannot use metric in numeric computation directly — no explicit conversion mechanism. Intentional: such crossings should always be explicit and visible. (D1 §4.8)
    Q: Why is R3 "defensive dead code" — and why keep it?
    A: Grammar <field_value>::=int|float|str|bool never produces MetricLiteralNode in arithmetic position. Parser rejects accuracy+0.5 syntactically — TC never sees it. R3 is over-specification: the grammar already enforces what R3 checks semantically. Kept because if grammar were extended to allow expressions in field positions, R3 would activate correctly. It documents intent for future extensions.
    Q: Why is int→float coercion NOT in the TypeChecker?
    A: D2 TypeChecker does not implement a formal T⊢e:τ judgement system — it checks structural constraints (is this model declared?), not expression types. Coercion is stated as design intent in §4.5 and grounded in the interpreter via Python's own numeric widening at BinOpNode eval. Scope decision consistent with handout requirements.
    Q: evaluate e.best on d.train — DataLeakageError?
    A: NO. R5 only covers TRAIN statements using .test split. Top-level evaluate on d.train is syntactically valid, passes all 5 type rules, and runs to completion. Result will have inflated metrics (model evaluated on its own training data) but Ayar does not detect this as an error by design — DataLeakage is defined only for training on test split.
    Q: What was wrong in the original E-ExperimentBlock and why is the fix semantically correct?
    A: Original wrote M' in output state — experiment-internal metric data would propagate to outer scope, contradicting both the prose "M' is not propagated" and §4.6 stack-dynamic lifetime. Fix restores outer M unchanged, discarding inner M'. Only R' (best selection) escapes via exp_name.best key in Γ. Found via AI audit cross-referencing formal rule against prose.
    Q: Why is the experiment record structured type described with name equivalence?
    A: Two experiment blocks with identical internal structures are NOT interchangeable. iris_exp.best and titanic_exp.best are different Γ keys. Name equivalence: the experiment name is the type identity — prevents accidental result substitution across experiments. (§6.5–6.7, §6.14)
    Q: Three-step logical chain for metric≠float enforcement:
    A: (1) Name equivalence → metric≠float regardless of identical ℝ representation — different names = different types. (2) No coercion rule metric→float exists (§4.7 permits only int→float). (3) All arithmetic and relational operators require operand-type identity — since metric≠float and no coercion closes the gap, any expression mixing them is rejected.
    Q: Why is assignment a statement not an expression in Ayar?
    A: Reliability and readability (§1.3.1, §1.3.3). C-style if(x=0) confusion is a well-known bug source. Ayar target users are ML researchers not PL specialists — confusion between assignment and comparison could cause wrong model selection. Assignment as statement: only in model field declarations (k=3) and analyze fields (threshold=0.08). Cannot appear inside expressions. Trade-off: no chained assignment, no assignment-in-expression shortcuts. (§7.7)
    Q: Why no short-circuit boolean evaluation in Ayar?
    A: Expressions in Ayar have NO side effects whatsoever — short-circuit semantics derive value only when evaluating second operand has a side effect that should be skipped. In exclude if overfit or underfit, both tags are pre-computed Booleans already available. Full evaluation: behavior completely predictable regardless of operand order → supports reliability (§1.3.3). Trade-off: if conditions become computationally expensive in future extension, full eval wastes work. (§7.6)
