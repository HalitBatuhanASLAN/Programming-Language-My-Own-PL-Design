    Design Decision Q&A (Exam-Focused)
    Q: Why is the two-step tag-then-filter design (P-Analyze + P-Exclude) better than a single combined rule?
    A: Separates concern of analysis (what is the model's fitness status?) from policy (which models to eliminate?). Reader can audit each independently — analyze block states thresholds, exclude statement states policy. Combined rule would fuse two distinct concerns into one opaque operation. §1.3.1 readability: self-contained statements each doing one thing are easier to review. E-Sequence sequential structure also requires tagging before filtering in state — combined rule would hide this ordering requirement.
    Q: Why does Ayar fail LOUDLY with NoEligibleModelError instead of silently returning an overfit model?
    A: Reliability priority (§1.3.3). In ML model selection, silently returning an overfit model would cause wrong conclusions about model quality — the user would trust a model that generalizes poorly. Loud failure (runtime error) forces the user to confront the problem: relax thresholds, add more models, or reconsider the experiment design. P-SelectBest failure case is a deliberate design decision documented in D1 §4.4.
    Q: Why does data leakage detection happen at type-check time for TRAIN but not for top-level EVALUATE?
    A: R5 is defined specifically for training on the test split — this is the classic data leakage scenario where future test data contaminates training. Top-level evaluate on any split is permitted because evaluating a final model on training data, while potentially misleading, is not a leakage violation by Ayar's definition. The distinction is deliberate: training uses test data → catastrophic leakage. Evaluating on training data → inflated metrics, but user's choice.
    Q: Why is the experiment record NOT fully accessible from outside the block?
    A: Encapsulation design decision (D1 §4.8). Internal metrics, overfitting tags, ranked ordering are implementation details of the pipeline. Allowing them to leak outward would make user code dependent on internal block details — any future change to how metrics are computed would break external code. Only best survives via export. Trade-off: user cannot access a specific model's validation accuracy from outside, making certain debugging scenarios harder. But Ayar's intent: good results obtained without needing to debug intermediate steps.
    Q: Why does collect metrics restrict M but not delete eval_accuracy?
    A: P-AnalyzeOverfitting reads train_acc and val_acc (stored as eval_accuracy) to compute the overfitting tag. If collect metrics [f1, precision] runs BEFORE analyze (which it does via E-Sequence), accuracy would be removed from M. Analyze then reads metrics.get('accuracy', 0.0) = 0.0 → 0.0 < underfit_max_acc → ALL models tagged underfit. Bug discovered in sample_2.ayar stress test. Fix: eval_accuracy is a separate field in ModelResult, never touched by E-Collect.
    Q: Why is the expression sub-language defined but never semantically formalized in §4.4?
    A: Scope decision per handout (only 2 constructs required for formalization). The expression hierarchy (add_expr, mul_expr, etc.) exists in the grammar and parser but has no evaluation rules in §4.4. This left R3 as dead code — grammar prevents metric literals in arithmetic, so R3 can never fire on real parsed input. D5 retrospective: this is the main gap in the spec. A full implementation would need T⊢e:τ judgement rules and an expression evaluator in the interpreter.
    Q: From Part 1 — what are the 3 DSL-specific constructs that prove Ayar is NOT a generic scripting language?
    A: (1) compare by f1 higher_is_better — metric-aware ranked comparison, no generic language has this built-in as a statement. (2) exclude if overfit or underfit — domain-specific model fitness filtering using tags computed by the pipeline. (3) select best — automatic winner selection from ranked, filtered model set. Together: Compare–Exclude–Select is the DSL-identity construct. No generic scripting language (Python, JS, etc.) has these as first-class language constructs.
    Q: Why is the or keyword in exclude if X or Y NOT the same or as in expressions?
    A: exclude_condition has its OWN closed sub-grammar: <exclude_condition> ::= <exclude_term> { "or" <exclude_term> } where <exclude_term> ::= "overfit" | "underfit". If routed through <expr>, the or in exclude if overfit or underfit would parse as a general boolean expression — and then exclude if accuracy > 0.5 would also be valid, which we don't want. Closed sub-grammar restricts domain to only the two legal conditions. E1 experiment AI caught the or keyword collision — you adopted the closed sub-grammar fix.
    Q: BinOp tree for: accuracy > 0.80 and f1 >= 0.75
    A: BinOp('and', BinOp('>', MetricLit(accuracy), Lit(0.80)), BinOp('>=', MetricLit(f1), Lit(0.75))). Process: 'and' at <and_expr> level. Each side resolved at <rel_expr> level (higher precedence = deeper nonterminal = resolved first). accuracy and f1 are MetricLiteralNodes — not IdentifierNodes. This matters for R3 in the type checker.
    Q: Describe the scope chain lookup for model m referenced inside experiment e2, when m is declared globally.
    A: Static (lexical) scoping lookup (§5.7): (1) Check e2's own inner scope — is m declared here? NO. (2) Move to global scope — is m declared here? YES (ModelDecl type=KNN name=m). Resolved. Same result whether called from e1 or e2 — source code readable, runtime-independent. If dynamic scoping: would follow call stack, not source structure — nondeterministic for two experiments sharing the name m.
    Q: What is the lifetime of iris_exp.best after the experiment block closes? Where does it live?
    A: After export: lives in Γ (global environment) under key 'iris_exp.best'. Lifetime = STATIC (§5.8.1) — bound when experiment block closes, persists until program terminates. Contrast with internal M: stack-dynamic, discarded at block exit. iris_exp.best is the only piece of experiment-internal state that escapes via E-ExperimentBlock's export conclusion.
